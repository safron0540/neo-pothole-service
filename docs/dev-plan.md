## Правила: ветки, коммиты, PR

Аналогия: `main` это чистовик диплома, ветка это черновик одной главы. В чистовик глава попадает только после проверки.

- **Ветки.** `main` защищён, прямых пушей нет. Работа идёт в ветках от `main`: `feat/…` (функция), `fix/…` (баг), `docs/…`, `test/…`, `chore/…`, `ci/…`. Одна ветка живёт не больше 2–3 дней и делает одно дело.
- **Коммиты.** Формат `тип(область): что сделано`, тип по-английски, описание по-русски, в конце строка `Refs: REQ-040` (если есть требование). Типы: feat, fix, test, docs, chore, ci, refactor. Пример: `feat(requests): идемпотентная подача заявки по client_request_id`.
- **Размер.** Один коммит это один смысл, один PR до 400 строк без учёта миграций и тестов. Больше значит разбить.
- **Порядок внутри PR.** модель и миграция → сервис → роутер → тесты → правка документов. Тесты в том же PR, что и код.
- **Слияние.** Только Squash and merge при зелёном CI и одном одобрении ревьюера; после слияния ветка удаляется. В `main` остаётся один коммит на PR с названием PR.
- **Документы.** Правка в БД идёт одним PR: миграция → `docs/db-schema.md` → ER → ЧТЗ. Так документы не расходятся с кодом.
- **Без упоминаний ИИ-помощника.** В сообщениях коммитов, описаниях PR, комментариях и файлах нет строк соавторства ИИ-помощника (`Co-Authored-By`), ссылок на его сессии и подписей «сгенерировано …». Автор всех коммитов — Артём Бердников.
- **Откат.** Ошибку в `main` исправляет новый PR `fix/…` или `git revert` слитого коммита, историю не переписываем.

## Защита main и CI

CI это автоматический входной контроль: как охранник в университете, который не пускает без пропуска. Шаги в порядке запуска, провал любого останавливает всё остальное.

| Шаг CI | Команда | Что ловит |
| --- | --- | --- |
| 1. Стиль | `ruff check .` и `ruff format --check .` | ошибки в коде, неиспользуемые импорты, разнобой формата |
| 2. Миграции | `alembic upgrade head`, потом `alembic check` на чистой PostGIS-базе (отдельный job backend-integration, там же идут тесты с меткой integration и e2e) | миграция не применяется или модели расходятся с базой |
| 3. Тесты | `pytest -m "not integration and not e2e and not slow" --cov=app --cov-fail-under=60` (job backend-ci) | сломанная логика и покрытие ниже 60 % |
| 4. Образ | `docker build` бэкенда и ML-заглушки | код собирается, в контейнере нет пропавших файлов |

Настройки защиты ветки `main` (Settings → Branches):

- обязательный PR и одно одобрение; новый коммит в PR сбрасывает одобрение
- обязательные проверки: одна проверка `CI gate` (она собирает итог всех jobов CI); ветка должна быть актуальной относительно `main`
- запрет force-push и удаления `main`, разрешён только Squash merge, автоудаление ветки после слияния
- правило действует и на администраторов, иначе владелец репозитория сливает сам себя без проверки

Порог 60 % включён сразу в PR 1-1: покрытие считается только по `app/core/*` и `app/modules/*/service.py`, а пока этих файлов почти нет, порог проходит. Код выхода 5 («тесты не найдены») CI считает нормой.
